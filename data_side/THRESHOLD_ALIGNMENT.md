# 数据审计到直接检测门槛的落实

本轮修改针对两个可复现的不一致：分类器把根因网元 `cpu_usage` 约 0.9 的小幅相对变化判作 CPU 故障，而直接检测只接受 `cpu_usage ≥ 18`；FRR 普通 `err` 日志曾单独打开事件，第一批数据却有 1,410 条重复的 OSPF `Could not send entire message` 错误文本。修改位置为 `aiops_v2/classification/semantic.py` 和 `aiops_v2/detection/direct_evidence.py`。

| 证据 | 现行处理 |
| --- | --- |
| CPU、磁盘、内存字段的量程不同，磁盘还有 47 个单元大于 100 | 分类与直接检测共用量程门槛：CPU ≥ 18、磁盘 I/O ≥ 55、可用内存比例 ≤ 0.90；不裁剪大于 100 的磁盘原始值 |
| 低基线上的极小相对变化可得到很大的分类得分 | 分类还要求同实体事件前后绝对变化至少为 CPU 12、磁盘 I/O 50、可用内存比例下降 0.06、进程数增加 30；这些下限来自现行直接证据强度门槛与量纲地板的乘积 |
| 大量重复的普通 FRR `err` 日志缺少独立状态变化 | `err` 与 `warning` 留在日志和根因排序辅助证据中，不单独打开事件；`crit`、`alert`、`emerg` 仍可即时触发，路由状态指标仍可直接触发 |

这些是**已有直接证据门槛的跨环节对齐和日志触发约束**，不是基于第一批真值标签拟合的最优参数。分类使用同一实体事件前最多 30 分钟的观测中位数作变化参考，不用其他网元的绝对水平替代该实体基线。普通 FRR 错误可能伴随真实故障；若路由状态指标能观察到异常，它仍能触发事件。只在日志中可见的真实故障存在漏检风险，须待真值标签验证。

## 回归与无标签对照

- 公开三例使用官方评测器：TP 3、FP 0、FN 0、Total 96.011111；摘要保存在 [门槛运行对照](results/threshold_comparison.json)。三例全为资源故障，不能验证路由故障召回。
- 本轮在同一特征库与推理框架下保存的调整前对照为 473 个第一批候选，有定义锚点的类别中 137 条证据不足；调整后的推理为 403 个候选、201 条有锚点支持、0 条锚点证据不足、202 条类别尚未定义审计锚点。摘要保存在 [门槛运行对照](results/threshold_comparison.json)；逐事件预测和审计文件由本地重跑生成，`runs/` 不提交到 Git。类别变化和事件减少属于**输出变化**，没有第一批真值时不能称作误报减少或准确率提高。
- 更早的 587 候选报告来自另一时点的代码运行；本轮对照使用上述 473 候选快照，不把 587→403 全部归因于上述门槛修改。

后续收到完整故障标签与确认正常时段后，应按城市和时间留出验证集，分别评估普通 FRR 错误降级带来的召回风险、资源类别门槛对分类准确率的影响，再调整数值门槛。所需数据见 [标签契约](LABEL_CONTRACT.md)。

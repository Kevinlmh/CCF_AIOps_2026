# v3 第一批 8.827 → 9.15 对照审计（2026-09-30）

## 判断依据

用户提交第一批保守版 316 条预测，官方反馈 8.827，较此前标准版 8.71 只增加 0.117。平台没有提供 AD、RCA、类别或 TP/FP/FN 分项。第一批完整标签与第二批数据仍缺失；不能把预测数与官方第一批 292 条故障数的差额当作误报数，也不能从总分反推出各模块准确率。

用户随后提交仅补充 OSPF Cost 的第一批 321 条预测，反馈得分 **9.15**，比 316 条版提高 **0.323**，比 375 条标准版提高 **0.44**。这是同一输入和同一保守配置下的单变量对照；旧 316 条的时间、类别、Top-5 均未变化，因此增益与新加入的五条 OSPF Cost 候选有关，但没有分项反馈，仍无法断定五条中有几条匹配真值。

当前 316 条中有 135 条没有根因设备的直接异常证据，主要来自业务探针；这些事件的 Top-5 候选需要谨慎看待。此前缩减 59 条短时 CPU 候选只获得很小总分变化，继续按事件数量硬筛选缺乏证据。

## 本轮可复核的缺口

`routing.ospf6_interface_cost` 在第一批四台路由器上有五段从通常的 1 升至 100 或 400 的持续变化（长度 2、8、12、12、14 分钟）。v3 原规则未读取这个已存在的特征，因此完全漏掉官方 `routing/ospf6_cost_anomaly` 类。新增有物理量级约束、变化强度和连续分钟支持的规则及对应分类，并让从原始 CSV 新建的 v3 特征库保留该字段。输出 321 条，其中此前 316 条的时间、类别和 Top-5 均未改变，新增加五条 OSPF Cost 候选。它们具有明确异常证据，但在完整真值缺失时仍不能称作真阳性。

业务错误率与延迟也原先没有按请求量加权。新增可选 `--request-aware-service`：读取 `traffic.<flow>.requests_rate`，按 `requests / (requests + 30)` 调整服务症状分数；缺失或零请求不会伪造有效样本。原始 CSV 构建器补充该请求速率特征，并按相邻两次计数器观测的实际间隔计算速率，避免缺失分钟时高估。第一批与保守版对照后事件数为 317，但有 95 条旧预测不再逐项相同，且部分低请求量下的 Auth 延迟类别变化明显；由于真实超时也可能降低请求量，这个开关保持默认关闭。

单探针业务异常还可能来自发起探测的网元或其路径，而原 Top-5 只按目标城市的固定名称排序。新增可选 `--source-aware-candidates`，把已知的探针来源 `traffic-vm` 放入候选但不置于目标服务实例之前。第一批事件数仍为 321，58 条旧 Top-5 发生变化；缺少接口对端和域名到实例的权威映射，故该开关也保持默认关闭。两项可选开关均不改变 LLM 两阶段根因排序和类别判定接口，证据哈希仍随候选集变化。

## 尚未找到充分证据的方向

审计了第一批接口和路由维度序列：BGP peer 维度变化与现有聚合检测基本一致；OSPF 邻居状态、IPv6 route exists、接口 carrier/error/drop 按现有可信量级没有可触发变化。FRR OSPF 日志虽多，但绝大多数是 `Could not send entire message` 和 `Operation not permitted`，且对应路由状态没有同步变化，不能单独当作 OSPF 故障。链路、防火墙策略、软中断及其他路由配置类别继续缺少可靠事件锚点；需真实标签、权威映射或服务器 LLM 诊断实验支持进一步扩展。

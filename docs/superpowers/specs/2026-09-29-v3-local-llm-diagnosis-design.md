# v3：本地开源 LLM 参与根因与类别决策的完整赛题方案

日期：2026-09-29
分支：`v3`
状态：设计稿；2026-09-29 根据磁盘约束调整为 Mac 无模型权重、服务器可选 LLM。本文不等同于已验证的性能结论。

## 1. 目标、范围与证据边界

目标是由同一个项目完成七源数据接入、质量审计、事件检测、根因 Top-5 排序、官方故障分类、结果校验及评测。后续工作不再按“数据侧 / 模型侧”拆成两条互相依赖的交付线。输入与输出以 `docs/requirements/AIOPS_OnePage.md`、公开配置及评测器为准：输出事件时间、80 个合法网元中的 Top-5、28 个合法故障小类之一；时长与全局事件约束继续由官方契约校验。

用户已反馈：只提交第一批预测的 v2 无 LLM 与 API 复核结果均为 6.95 分；当前评分覆盖第一、第二批且测试满分为 60 分，因此 6.95 不能当作完整数据的 v2 总成绩。该同分结果只能说明本次末端复核没有带来可见得分增益。仓库内第一批 403 事件的本地 A/B 中，LLM 接受 27 次、回退 99 次、未采用 5 次、跳过 272 次；Top-1 改变 11 次、类别改变 0 次。第一批无完整真值，不能从这组差异推断准确率。

公开三个 Case 已用于调试且全是资源类；它们只能做契约与退化回归。第一批 403 个候选不能当训练标签，官方披露的故障总数不能当候选截断目标。拿到第二批并生成两批合并提交前，不比较完整竞赛分数。

## 2. 方案选择

| 方案 | 长处 | 主要问题 | 决定 |
| --- | --- | --- | --- |
| 直接恢复 v1.6 检测与 BiAn LLM 流程 | LLM 进入定位及分类，改动较快 | 旧检测的缺失语义和证据审计不如 v2；多轮逐候选调用成本高 | 作为对照 |
| 在 v2 最后增加更强 LLM 复核 | 最少改动 | 事件与 Top-5 已被前级锁定，无法恢复漏掉的根因；现有 A/B 无类别变化 | 不作主线 |
| v2 数据底座 + 新事件候选层 + 本地 LLM 两阶段诊断 | 保留七源质量控制，让模型实际决定 RCA 和类别 | 需要重建模块边界并实测本地推理资源 | **v3 主线** |

v3 继承可验证的数据解析、缺失掩码、行数守恒、官方网元与类别配置，以及评测器。检测借鉴 v1.6 的逐序列变化点思想和 v2 的直接证据/症状分层，但不直接沿用任一版本的最终事件门控。参考 `multi-agent-aiops` 的阶段状态、证据追踪和失败恢复接口；不引入与本赛题输出无关的自愈、审批、Kafka 或 Neo4j 服务。参考 BiAn 的“候选分析 → 比较排序 → 条件分类”，不复制其所有多轮调用。

## 3. 目标数据流与接口

```text
第一批/第二批七源 CSV
  → SourceManifest + CanonicalObservation（原始字段、单位、网元、时间、观测掩码、来源）
  → 版本化分钟特征库 + 数据质量审计
  → 多通道 EventProposal（可追溯触发证据）
  → 全局事件合并、分裂与时间边界确定
  → EventEvidencePack（前/中/后窗口、直接证据、症状、反证、缺失、已证实拓扑）
  → CandidateSet（约 8–12 个有依据的合法网元，含候选进入原因）
  → 确定性根因排序及分类 → 可选 LLM 对同一证据包重新排序及分类
  → 规则与证据校验、确定性回退
  → 官方 predictions.jsonl + 独立审计与运行清单
```

`EventProposal` 至少包含时间区间、城市/实体、候选通道、强度、触发证据 ID 和来源版本。`EventEvidencePack` 的每条证据包含网元、指标、原值、基线、变化方向、时间范围、数据源、观测状态及证据角色（直接、传播症状、采集质量、反证）。模型只读截断后的证据包；原始行可通过证据 ID 追溯，不把 96 GiB 原始数据塞进 prompt。

数据侧已有的重要事实进入接口，而不被代码默默假定：第一批八个 `monitor-vm` 缺观测；接口到实际链路对端、服务域名到具体实例尚无权威映射；部分 CR 的 BGP 数值结构性缺失；`disk_io_util` 有超过 100 的值，其物理含义待核准。缺失不填零，未知关系不编造成拓扑边。模型可提出间接根因，但审计须明确其缺少本机证据。

## 4. 事件检测与边界

检测器先产生候选，再决定输出事件，避免一个门槛同时承担“找线索”和“拒绝事件”两种职责。

1. **设备直接通道**：CPU/负载、内存、磁盘、进程、接口错误与状态、明确路由状态、严重 FRR 日志。使用同实体同维度的历史参照、变化点和持续性；物理量程是证据分量，不把现有固定阈值当真值。
2. **业务质量通道**：请求量校正后的 DNS/Web/Auth 失败、延迟、丢包与吞吐质量，按观测者和被测目标分开。普通流量体积与 NetFlow 不单独证明目标网元故障。
3. **辅助通道**：NetFlow、普通 FRR 日志、scrape health 和拓扑传播，仅补充或反证候选；采集失败不能被当成业务跌零。

同源重复指标在事件形成前折叠；跨城探针对同一目标的症状去重。候选事件按时间与证据关系合并或分裂，最终满足官方时长和全局匹配约束。每次合并、拒绝及边界调整记录原因。v1.6 与 v2 检测器保留为可独立运行的对照，不用它们的预测充当 v3 标签。LLM 不做逐分钟主检测；若以后让模型判断边界模糊事件，必须作为单独消融实验，而不是暗中改变检测输出。

## 5. 根因候选与本地 LLM 决策

确定性候选检索面向召回：综合本机直接异常、时间领先、恢复、已证实依赖关系和症状解释能力生成约 8–12 个候选；保留跨城候选与低观测候选的进入依据，不在 LLM 前先截成 Top-5。候选数上限是 prompt 预算，不是城市或故障类型的硬过滤。候选覆盖不足时在审计中单列，不能让 LLM 为未提供的网元负责。

**Mac 阶段不下载或加载 LLM 权重。** 默认 `rules` 模式完成事件检测、候选根因排序、官方分类与合法提交，且每个事件输出可复现的证据包。可选 `llm-jsonl` 模式读取服务器批量生成的诊断结果，严格校验候选、类别及证据 ID，失败时退回同一事件的确定性诊断；模型不可改变已冻结的检测事件边界。证据包与请求/响应使用版本化 JSONL，两个模式使用相同事件和候选集，便于只比较诊断差异。

服务器阶段再从 Hugging Face 选择并下载模型。候选包括 [`Qwen3-8B-4bit`](https://huggingface.co/mlx-community/Qwen3-8B-4bit) 与 [`Qwen3-4B-Instruct-2507-4bit`](https://huggingface.co/mlx-community/Qwen3-4B-Instruct-2507-4bit)；若服务器不是 Apple Silicon，改用相应原始权重和适配的推理后端。模型选择由服务器内存、每事件耗时、合法 JSON 比例和诊断质量实测决定。模型仓库、revision、量化及运行库版本写入运行清单。

模型调用分两步：

- **RCA**：给出候选网元、直接/传播/反证的紧凑证据和已验证拓扑，要求比较哪些候选能解释其他异常、哪些只是下游症状；输出候选排序、逐候选证据 ID 与简短理由。重点评测合法候选覆盖与 Top-5 排序，不把模型自报置信度视为已校准概率。
- **分类**：以高位根因候选为条件，比较官方 28 类中可能的“网元—故障类型”组合；输出首选组合及关键支持/冲突证据。最终 Top-1 与类别必须来自同一可解释组合，Top-5 从候选根因排序产生。

服务器原型限制证据包与输出 token 预算，保持同一模型、prompt、参数在对照中不变。8B 的思考/非思考模式分别做小规模格式与质量实验；思考模式依模型卡建议采样，不假设贪心解码最佳。默认每事件两次模型调用，只有证据冲突或格式失败才进行一次受限重试。输出做严格 JSON、合法网元、类别、证据 ID、重复项校验；模型无响应、格式错误或引用不存在的证据时，记录失败原因并使用确定性诊断。缓存键包含模型 revision、prompt 版本、taxonomy 与证据包哈希，便于复现和避免重复推理。

## 6. 项目结构与运行产物

新增 `aiops_v3/`，按 `data/`、`detection/`、`events/`、`evidence/`、`localization/`、`classification/`、`llm/`、`evaluation/` 与 `run.py` 划界。`aiops_challenge_2026/` 保持公开契约和评测工具角色；`baseline/bian/`、`aiops_v2/` 保持可运行对照。现有数据审计和字段字典作为 v3 数据治理输入，不维护另一套独立“数据侧”主流程。

每次运行输出：官方 `predictions.jsonl`；机器可读事件/候选/模型审计；源清单和质量报告；模型与配置版本清单；资源及耗时报告。日志不写提交票据、密钥或大段原始 prompt。根目录现有 `submit.py` 含提交票据，不能纳入源码提交；实际提交仍由用户控制。

## 7. 评测设计与交付顺序

**阶段 A：冻结对照与数据契约。** 保存第一批两次 6.95 分提交对应的预测文件、代码/配置哈希和可复核输出；把第一、第二批统一导入同一清单格式。第二批尚未下载，当前不能声称完整赛题效果。公开三例做输入输出与证据链回归。

**阶段 B：事件候选与证据包。** 先让两个旧检测器和 v3 检测器在同一特征库分别产出候选，报告重叠、独有事件、触发来源和边界差异。合成故障验证变化点、缺失、跨城传播及 1–30 分钟约束；无真值全量只报告矛盾与分布，不称作精度。

**阶段 C：Mac 确定性全流程及服务器模型基准。** Mac 先从现有七源特征库和公开原始样例完成无权重诊断、合法输出、证据包与运行审计。服务器在固定事件和候选集上比较确定性诊断、BiAn 风格 LLM、v3 两阶段 LLM；分别记录 Top-1/Top-5/类别变化、合法输出率、回退率、内存和耗时。用公开样例确认基本正确性，但不在这三个答案上反复调 prompt 后宣称泛化提升。

**阶段 D：完整数据与官方反馈。** 获取第二批数据后，第一批与第二批分别生成结果、联合做 schema 校验和去重，再合并提交。按同一数据覆盖和官方规则比较 AD、RCA、大类、小类与总分；若平台只返回总分，应保留消融结果，不把单个总分差异错误归因给 LLM。任何阈值调整需留出时间/城市或已核实案例验证，避免仅对公开样例拟合。

开始实施前先将本规格拆成可独立验收的实施计划；阶段 A/B 的输出接口稳定后在服务器接入模型。Mac 阶段的完成标准是：现有第一批特征库及公开样例均可生成合法提交和逐事件证据审计，默认模式无模型依赖，固定事件上的可选诊断输入能被校验并安全回退。两批完整数据的成绩比较及模型收益验证仍须等第二批与服务器推理完成；当前不承诺具体竞赛分数。

## 8. 主要风险与回退

- 量化模型可能给出合法但错误的因果解释：保留确定性对照和证据反查，不以“有理由”代替正确性。
- 候选召回不足会限制任何 LLM：单列候选覆盖实验，允许有证据的跨城补候选，不凭模型想象新增官方网元。
- Mac 磁盘不足：本机不下载模型、不复制 100 GiB 级原始数据；读现有特征库或流式处理样例，产物写入已有被忽略的 `outputs/`。服务器另行存储权重与推理缓存。
- 第二批分布可能与第一批不同：分批审计、统一 schema、分批记录模型和数据版本；不沿用未验证的第一批阈值。
- 缺少正式全量真值和权威拓扑映射：用可证伪的证据矛盾、公开样例、合成场景及同覆盖官方反馈做阶段决策，明确未能验证的结论。

# AIOps v2.1 模型代码对齐设计

> 状态：待评审。本文件定义从当前 v2.0 实现向 v2.1 迭代的模型侧设计；本阶段不修改生产代码、不调整数据读取、不删除文件。

## 1. 目标与范围

目标是在保留 v2.0 最新设计的多源张量时序架构前提下，修复当前实现中导致公开样例分数明显下降的决策链问题，并让代码实现与 [v2.0 架构设计](../../design/model-v2-architecture.md)一致。

本设计只覆盖模型和预测决策：异常分数、事件解码、根因排序、故障分类、可选 LLM 复核及相关测试。CSV 解析、数据目录发现、特征存储格式、数据清洗和数据侧映射均不在本次范围内；既有输入读取接口和官方输出 schema 保持不变。

v1.x 只作为离线基线和对照，不将其检测器、事件候选或规则隐式并入 v2.1 的主推理链。只有单独消融证明某个具体组件有泛化收益时，才另行设计是否复用。

## 2. 现状证据与问题定义

当前可复核结果：

- v1.6 三个公开样例报告为 96.01，三例根因与分类均正确，见 `outputs/v1_6/sample/report.json`。
- v2.0 冒烟结果为 42.67，三个样例均被匹配，但时间边界偏宽；一个根因未进 Top5，另外两个为第 4、第 5；后两例分类错误，见 `outputs/v2_0/sample_smoke/evaluator_report.json`。
- 该 v2.0 冒烟命令使用 `--epochs 1`，低于 `TrainConfig` 默认的 5 轮，因此分数不能单独作为 v2.0 默认配置的公平比较。
- v1.6 全量运行输出 723 个事件，而赛事公布总量为 292；没有全量标签可证明这些额外事件均为误报，但该结果足以说明不能把 v1.6 全量预测当作 v2.1 的正确答案或事件数目标。

代码审查确认的实现问题：

1. `aiops_v2/events/decoder.py` 用区间内高于 `keep_threshold` 的逐分钟能量累加打分，没有足够的区间长度归一化或弱尾部惩罚，因此较长区间可能仅因多包含低强度分钟而胜出。
2. `aiops_v2/localization/ranking.py` 在全网候选间累加节点、traffic 和 NetFlow 分数；观测/症状证据可能盖过根因设备的直接、先发证据。
3. `aiops_v2/classification/semantic.py` 根据根因 Top-1 的城市筛选分类信号。Top-1 若落在症状城市，真实根因城市的内存、磁盘等特征会被排除，定位错误进而传导成分类错误。
4. 当前训练实现主要优化重构、下一步预测和表示一致性；当前根因与分类仍为确定性打分。v2.0 架构文档中的合成故障训练、根因/分类可训练头和更完整的事件证据目标尚未落入代码。
5. 现有单元测试覆盖理想概率平台、直接节点分数、合法分类 schema 等基本路径，但缺少弱尾部、跨城症状压过根因、Top-1 错城时分类仍应使用全局事件证据等回归用例。

## 3. 目标架构

主流程继续遵循 v2.0，而不是退回 1.x：

```text
现有特征存储（本次不改）
  ↓
多源掩码时序编码器
  ↓
节点 / 边 / 日志异常分数与时间变化证据
  ↓
稳健校准后的全网分钟故障概率
  ↓
全局半马尔可夫区间解码
  ↓
事件因果子图与候选根因评分
  ↓
联合根因 / 分类证据决策
  ↓
可选 LLM 受约束复核
  ↓
官方 predictions.jsonl
```

保留 TCN 多源分支、观测 mask、滑窗重叠平均、全局事件时间轴、官方候选实体约束和可选 LLM 的职责边界。v2.1 的工作是补足各决策头，而不是增加另一条 v1 规则链。

## 4. 模块设计

### 4.1 异常分数与训练校准

保留 `MultiSourceDetector` 的 node/edge/log 三个时序分支和重构、因果预测任务。异常分数必须保留可解释分量，不让单一未校准的绝对幅度项直接主导最终故障概率：

- 观测值的稳健量程/水平偏离；
- masked reconstruction residual；
- next-step forecast residual；
- 起始变化与恢复变化；
- 可观测跨源一致性。

各分量在节点、边、日志模态内分别稳健标定，再形成 family scores；校准过程记录中心、尺度、有效观测数及所用时间段。缺失模态不得按正常零分数处理；该模态应由 mask 表达为不可观测。

在不使用 `ground_truth.jsonl` 的前提下，按架构文档补充两阶段训练：先做真实无标签窗口的自监督训练，再从低异常参考窗口生成语义受控的合成扰动，用于训练根因/类别头。合成训练只使用通用字段语义和 taxonomy，不使用公开案例时间、ID 或真实标签。合成头不能绕过实际事件证据单独创建事件。

训练日志需记录每轮各损失分量、验证/参考窗口分数分布、固定随机种子、训练轮数和 checkpoint 元数据。冒烟测试可用 1 轮；性能比较必须用相同的默认训练配置，不得把 1 轮冒烟结果当作正式 v2.1 结果。

### 4.2 全局事件解码

继续使用全局、非重叠半马尔可夫解码，硬约束故障长度为 1～30 分钟，事件间隔先验为软约束，不以公布的 292 个故障数作为目标。

候选区间分数改为组合证据而非单纯累加分钟数：

- 区间平均与峰值故障概率；
- 起点的概率变化和最早直接证据；
- 区间内多源支持的一致性；
- 结束后的恢复/回落证据；
- 受控的长度先验和断点惩罚。

弱于持续性标准的尾部不应只因概率略高于保留阈值而延长事件。若区间内部出现强恢复谷值，应允许拆成两个候选；间隔较短但证据独立的事件不得被软间隔先验强行合并。解码器必须输出边界分项审计信息，供区分模型概率拖尾与解码目标偏差。

### 4.3 根因排序

每个候选根因均计算并保留分项分数：本机直接异常、时间领先、持续性、故障后恢复、因果边支持、数据可观测性及 observer/symptom 惩罚。直接且先发的本机证据为主；traffic 目标侧证据和 NetFlow 只能按关系语义支持候选，不能因高流量自动抬升观察者或远端症状节点。

候选仍允许来自任何官方城市，避免硬性的同城规则漏掉真实跨城根因。城市和设备角色作为可审计的软先验；所有候选分数和 Top5 变化都可追溯到事件子图证据。合成根因头的输出必须与证据分数融合，并允许在证据不足时保持低置信度，不得覆盖明显冲突的直接证据。

### 4.4 根因与分类解耦

分类不再只读取 Top-1 根因城市。设计为对事件内多个候选分别计算 candidate-conditioned 类别证据，并结合候选根因分布形成联合分数：

```text
root_logits       [K_event, N]
category_logits   [K_event, N, C]
joint_score       [K_event, N, C]
```

`N` 为官方网元数，`C` 由官方 taxonomy 动态读取。分类分数允许使用整个事件子图和各候选城市的局部证据；当根因 Top-1 暂时错误时，其他候选和事件级因果族证据仍可支持正确类别。最终输出根因 Top5 和一个最高可信的合法类别，均保留局部证据、反证和置信度。

在 learned head 尚未通过验证前，确定性语义打分仅作为可解释特征/回退，不得将 Top-1 根因城市当作硬过滤器。低置信结果应输出审计信息，不得为凑类别而无证据地选择某一类别。

### 4.5 LLM 边界

LLM 仍为可选的最后复核器，只能在本地事件、候选根因及 taxonomy 约束内提出有限重排或分类建议；不能改动事件时间、创建/删除事件、补造网元或读入 ground truth。接口和 JSON 校验沿用现有实现，不作为本阶段的性能依赖。

## 5. 代码边界与文件责任

预计后续实现主要修改：

| 文件 | 责任 |
|---|---|
| `aiops_v2/models/detector.py` | 输出可校准的分项异常证据，维持多源 TCN 与 mask 语义 |
| `aiops_v2/training/trainer.py` | 自监督训练、确定性训练记录和训练/参考窗口流程 |
| `aiops_v2/training/calibration.py` | 分模态稳健校准及可审计统计 |
| `aiops_v2/training/inference.py` | 将重叠窗口分项分数稳定回写分钟时间轴 |
| `aiops_v2/events/decoder.py` | 长度受控、显式建模 onset/recovery 的全局区间解码 |
| `aiops_v2/localization/ranking.py` | 证据分解式根因候选排序 |
| `aiops_v2/classification/semantic.py` | 与 Top-1 城市解耦的候选条件分类和 taxonomy 映射 |
| `aiops_v2/run.py` | 串接各头、验证输出并记录完整审计数据 |
| `aiops_v2/training/synthetic.py`（新增） | 依据公开语义生成可复现、非案例特定的合成故障训练样本 |
| `tests/v2/` | 决策头单测、跨模块回归和输出契约测试 |

保持 `aiops_challenge_2026/schema.py`、官方 evaluator、公开实体/taxonomy、feature store 接口和当前 LLM 后端契约不变。本设计不修改 `baseline/bian/preprocessing/` 和 `aiops_v2/data/`。

## 6. 精简与删除原则

本项目目前没有证据支持整体删除 1.x 或 v2 模块。精简按引用关系和行为覆盖逐项审计，不做目录级清理：

- 保留 1.x 代码作为可复现实验对照；在 v2.1 主流程中不调用它。
- 保留 evaluator、schema、官方 config、`tests/v2` 和现有 v2 checkpoint 格式兼容，除非证明无任何用户产物依赖。
- 保留 LLM 适配器，因为它是已约定的可选后续能力；此次不扩展其职责。
- 仅可删除同时满足以下条件的内容：没有生产/测试调用者、不是公开契约或 checkpoint 兼容层、无用户结果/文档依赖，并且删除后完整测试通过。
- `fault_probability` 当前仍被模型测试断言，不能直接视为死代码；若未来移除，必须先明确废弃接口、同步测试和文档。
- `outputs/v1_5`、`outputs/v1_6`、`outputs/v2_0` 是性能对照和失败证据，不能在 v2.1 通过验收前清除。

## 7. 验收设计

### 7.1 单元与合成行为

新增下列可重复的、带已知注入边界的合成测试：

1. 1 分钟高置信故障不得因最短时长规则被漏掉；30 分钟故障不得截断前后边界。
2. 高概率故障平台后接弱概率尾巴时，结束时间应在持续故障证据消失附近，不因尾部正值机械延长。
3. 一个事件内部有显著恢复谷值后出现独立强峰时，应输出两个事件；仅短弱间隙时允许同一事件。
4. 远端 NetFlow/traffic 症状不得在没有直接/先发因果证据时压过直接根因；真实根因允许跨城，且不因城市先验被硬过滤。
5. 根因 Top-1 在症状城市时，真实根因城市的内存/磁盘证据仍可支持正确分类。
6. 每条输出仍符合官方 JSONL schema，根因 Top5 合法、唯一，类别来自 taxonomy。

### 7.2 对照比较

- 统一随机种子、输入 feature store、设备和默认 `epochs=5`，记录 v1.6 与 v2.1 的三个公开样例逐项 evaluator 指标；1 epoch 只用于 pipeline smoke。
- v2.1 晋级目标是公开样例总分至少不低于 v1.6 的当前基准 96.01，并单独列出 AD/RCA/Major/Minor/TP/FP/FN。该门槛是防回退的回归条件，不是泛化证明，也不能通过只围绕三个样例定制硬规则来满足。
- 必须同时通过合成测试。若公开样例分数提高但合成故障行为退化，不得判为通过。
- 全量数据暂不作本次执行要求；未来运行只审计概率/持续时间/城市分布和资源消耗，不把 292 写入阈值、损失函数或输出数量控制。

### 7.3 解释与可观测性

每个事件审计日志至少包含：解码边界分项分数、模型各模态概率/残差、Top5 根因分项、类别候选分项、候选淘汰原因、校准统计和 LLM 是否覆盖本地建议。评测失败时能定位到 detector、decoder、localizer 或 classifier 中的具体层。

## 8. 风险与限制

- 公开样例只有三个，不足以证明全量泛化。即使达到 96.01，也只代表不低于当前公开回归基线。
- v1.6 的 723 条全量输出与 292 的赛事口径存在明显差距；没有全量真实标签前不能把 v1.6 当成 ground truth。
- 合成扰动可能与真实故障形态不一致，因此只允许辅助训练定位/分类头；每类扰动都应有单元测试和消融结果。
- 只有在模型、校准和解码分别记录证据时，才能判断修正来自哪一层；一次叠加多项变更不能用于验收归因。

## 9. 本阶段明确不做

- 不实现上述代码变更；需用户审阅本文后再写实施计划。
- 不更改数据读取、CSV 字段、特征存储或官方 schema。
- 不调用 v1.x 事件输出作为 v2.1 兜底，不以目标事件数进行截断。
- 不删除历史代码、测试、结果、checkpoint 或用户文件。
- 不接入真实 LLM，不使用隐藏标签或人工标注测试数据。

# v3 检测与特征库复核（2026-09-29）

## 已知成绩与验证边界

用户提交第一批标准版 375 条预测，反馈得分 8.71，高于此前 v2 的 6.95；随后提交第一批保守版 316 条预测，反馈得分 8.827。比赛测试总分为 60，且完整评测需要两批数据；当前没有第一批完整真值或第二批数据，因此本轮不能计算隐藏集 TP、FP、FN。官方第一批 292 条是故障真值数量，不是预测条数截断线。

## 排查到的问题

1. 新批次原始 CSV 构建器原先把同一目标城市的 DNS、Web、Auth 和 Elephant 放在一条 `city:<target>` 边上。检测按边目标合并症状，可能把不同业务故障误合并。现在使用 `service-group:<target>:<flow>`，与第一批复用的 v2 特征库语义一致。
2. 同一服务边有多个原始监控序列时，构建器原先取最大的错误率。现在先按每条序列计算计数器增量，再按请求增量加权汇总错误率；不同城市和业务的计数器状态也分开保存。没有请求增量或错误增量的行不会伪造比率。
   多个独立公开 Case 也不能作为一个原始数据根目录混合建库；构建器现在要求分别指定每个 Case，以免重叠时间窗互相污染。
3. 原始公开样例第一例只有 23 个 CPU 观测分钟，其中故障覆盖了多数观测。整段中位数落在故障值上，导致从原始 CSV 新建的 v3 特征库漏检。现在仅对 8–59 个观测点的稀疏序列，用异常方向相反一侧的 20% 分位数估计基线及噪声；长序列仍用原中位数口径。第一批复用库的标准预测与之前逐字节相同。
4. 标准版第一批有一批短时、低强度、单设备、仅 CPU 指标支撑的事件。增加可选 `conservative` 配置：只在事件不超过 3 分钟、CPU 最高分低于 8、无其他直接类别、无业务症状且仅一台设备时筛除，并在运行清单记录拒绝理由。标准版仍为默认，不能把这条经验性筛选当成已验证的准确率改进。

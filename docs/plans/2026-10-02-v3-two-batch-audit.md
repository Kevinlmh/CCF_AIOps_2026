# v3 两批数据链路优化与复跑计划

## 目标与约束

以已评分的两批 397 条结果为对照，改善有可核查缺陷的诊断证据和分类回退，并建立可重复的最终预测审查。第一批原始 CSV 已不在本机，复跑使用现有 v3 特征库；第二批原始 CSV 在本机，但只有在确认建库缺陷时才重建。没有隐藏标签，不以预测条数推断准确率。保留服务器 LLM 的根因排序和分类接口。所有修改留在本地工作区，不提交、不推送、不覆盖 `result.jsonl`。

## 审计发现与取舍

- 现有第一批 321 条中，135 条根因没有直接设备异常证据。业务症状的 `evidence_id` 可追溯到特征库边，但导出的证据包未明确列出发起探测的 `traffic-vm` 和服务组目标。补充观测关系只供 LLM 理解来源，不据此改变规则候选名次。
- 检测器读取 `traffic.elephant.loss_rate`，分类回退却没有此类映射，可能输出无关的 `resource/cpu_pressure`。按官方类别将这一明确丢包症状映射为 `link/loss`；当前两批没有此类已检出事件，因此预期已评分预测不变。
- 全局健康尾部分位数、来源候选、同城合并等消融没有隐藏标签支持。健康尾部分位数在两批分别由 321→329、76→79，并集中新增多条同一设备 CPU 短事件；不升为默认。
- 第一批 9 个、第二批 1 个同类重叠事件对可能代表不同根因；现无权威物理对端映射，审计警示而不自动合并。

## 实施步骤

1. 测试先行：证据包包含可追溯的业务探针来源和目标，服务器证据导入及哈希往返一致；规则预测不变。
2. 测试先行：只有 `elephant` 丢包的事件正确归为 `link/loss`。
3. 测试先行：两批运行结果与合并文件审计检查官方格式、行数、唯一 ID、输入时段、证据哈希、输出哈希和逐行合并一致性，并汇总类别、证据级别与同类时间重叠。
4. 运行完整测试；按现有保守路由配置重跑两批，合并到新文件并运行审计；对照已评分 397 条文件逐字段比较。公开三例单独回归。
5. 记录实测差异、剩余风险和服务器交接影响。保持工作区未提交。

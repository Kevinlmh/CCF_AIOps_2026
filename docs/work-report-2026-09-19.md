# CCF AIOps 2026 阶段工作汇报

**日期**：2026-09-19

---

## 一、已完成的工作

### 数据接入

七个数据源的原始结构差异很大，node、interface、scrape是宽表，routing和traffic是长表，netflow是已按分钟聚合的五元组，frr是系统日志。已经为每一类写了独立的读取规则，统一成同一套观测契约，并全程做逐源行数守恒统计，写进推理日志供与数据侧对账。八城全量一次读入约5.2亿行。

节点归一负责把各种原始主机名映射到官方80个合法网元，映射不上的行不丢弃，记为过滤行进入审计。

### 检测流水线

整条链路是：解析 → 语义转换 → 逐序列在线打分 → 证据准入 → 事件切分 → 根因排序 → 分类。除最后一段的可选 LLM 复核外全部是确定性的。

系统底座是统一观测契约，每条观测的身份是 `(数据源, 网元, 指标, 维度)` 四元组。它决定了什么算同一条序列，所有滚动统计都在序列内部独立进行。这样切分的原因是：一条接口速率指标会因接口不同分裂成多条序列，其中大量是全程为零的备用接口，如果合并成一条，这些零值会把中位数拉到接近零，任何一点正常流量都会变成巨大的异常。

指标语义配置负责把原始观测变成可比较的量。累计计数器按真实分钟间隔差分成增量并处理回绕，每个指标带异常方向、事件角色和是否参与检测。

打分环节同时算两个互相独立的分数：
- 一是相对该序列自身近期状态的鲁棒偏离
- 二是值落在物理危险区间的位置。加第二个信号是因为只看相对偏离会出错。例如磁盘利用率从0.2%涨到45%，相对基线是两百倍，但45%在物理上并不危险，而官方真实故障是把利用率打到接近饱和。

此外还做了三件事解决实测中暴露的缺陷：
- 连续异常时冻结基线，避免长故障的值污染参考窗口
- 把接口吞吐、NetFlow、磁盘读写速率等划为support角色，只能补充已开启事件的证据，不能自己开事件
- 把CPU与load、磁盘利用率与读写速率、同一服务的成功率与错误率各折叠成一个因果族，避免同一原因的多种表现被当成多条独立证据。

事件准入要求trigger点满足状态证据、序列持续、跨族佐证或语义极值之一，之后按分钟能量做迟滞切分，并用官方给出的故障间隔先验做峰值抑制。证据在计算能量之前就按城市分开，每座城市独立完成准入和窗口生成，避免八城同一分钟的异常先合并再拆、事后无法完全分离。

### 根因定位与分类

根因排序为每个候选网元计算严重度、时间领先性、直接性、持续性、来源多样性、拓扑可解释性等特征再加权。其中直接性区分本机资源状态与远端流量症状，拓扑可解释性衡量该候选能在拓扑上解释多少其他异常节点，support证据统一降权。候选范围先收敛到有证据依据的城市，避免零证据城市靠字典序进入Top5。

分类把事件证据映射成稀疏的语义信号向量，再和官方28类故障原型做余弦相似度，减去反证、加上角色先验。信号按"分钟×信号"取最大值而不是累加，否则相关指标的字段数量会影响类别判断。

模型链路已在成都单城和八城全量两组数据上完整跑通。八城一次读入约5.2亿行，单次约两小时、峰值常驻内存2.4GB。两次运行都通过七源行数守恒检查，候选事件的时间边界全部落在赛题允许的1～30分钟内，没有出现无触发证据或跨城粘连的事件。

## 二、尚未解决的问题

**事件总量仍高于官方口径。** 官方说明第一批八城14天共292个故障，单城预期约36个，而成都最新一次跑出86个、八城全量跑出560个，分别是预期的2.4倍和1.9倍，说明还有一类系统性的误报没有定位到。

**分类类别覆盖不全。** 至今从未产出过 `link` 大类的事件，`firewall` 大类只出现过个位数。官方28类里有9类完全没出现过。这条与召回无关，是独立的一条线，原因还没查，但影响分类得分。

**验证手段只能间接衡量效果。** 公开样例的数据窗口是故障前后各约4分钟的裁剪片段，实测把检测阈值从7扫到24，三个样例始终各产出1个事件，因此样例对参数没有区分能力。当前只能靠签名覆盖率和长窗口反证这类间接判据评估改动，拿不到直接的准确率，也无法判断事件数的绝对值是否合理。

**置信度饱和。** 多数事件的置信度顶在上限，因为触发能量本身封顶。置信度目前不能作为真假故障的过滤依据。

**长故障只做了缓解。** 基线冻结解决了长时间故障下参考窗口被污染的问题，但当前打分架构本质上仍是离群点检测，而真实故障的形态是阶跃加持续平台，彻底替换需要引入变化点检测。

**LLM尚未接真实模型。** 管道完整、mock验证通过，但没接过真实权重，四个prompt还是官方原版，还未进行调整。

## 三、需要与数据侧协调的事项

**阈值标定。** 最需要的是各指标族的正常波动分布，各指标在14天里逐分钟差分的分位点。当前的指标尺度下限基本是估出来的，而早期最大的一类假阳性根因就是下限填错。

**根因定位。** 需要各源里所有标识取值到官方网元的映射表及映射不上的角色说明；需要接口到链路和对端设备的映射表，否则"哪条链路坏了"无法回答；需要DNS/Web/Auth域名到具体服务网元的映射，现在关系证据同时挂在三个节点上。

**数据完整性。** `monitor-vm` 是官方合法根因之一，但在正式数据里完全没有观测，公开样例里却有，需要确认是导出遗漏还是设计如此，若确实在它上面注入过故障，这些case的根因定位必然为零。骨干设备上的磁盘读速率全程为零，没有信息量。各城市数据量相差三倍，需要确认是真实流量规模不同还是采集范围不同。

## 四、后续方向

**解决大量的系统性故障误报。** 当前检测的故障数量远超官方给出的参考数，还需要加强故障检测定位。

**城市横向交叉验证。** 目前所有阈值都只在成都标定过，而八城结构同构，同一套配置在各城的行为应该在同一量级。做法是八城各跑一遍比较事件率、时长分布和类别分布，更进一步是在A城标定、拿到B城验证。这件事不需要标签，却能回答当前的事件数是否可信。

**查清分类类别覆盖问题。** 从信号映射和原型匹配两侧一起入手，这是当前影响分类得分的最大未知。

**接入 LLM。** 先修检测层的窗口质量再接模型，因为模型只会放大证据质量、不会纠正错误。接入时要同时做三件事：适配新增字段的 prompt、加失败降级到本地结果、加逐事件的结果缓存。

**用变化点检测替换当前的离群点检测。** 当前方法拿每个点与滚动中位数比较,而真实故障是阶跃加平台形态:故障持续超过窗口一半时中位数被故障值带跑,检测器失明,恢复时又会把回到正常误判为异常,现在只能靠冻结基线和尾部裁剪两个补丁绕开。换成变化点检测可以从方法上消除这类问题。
